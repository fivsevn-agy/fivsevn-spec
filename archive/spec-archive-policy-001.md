# Archive and Legacy Policy
# 历史文档与旧文件处理规则

本文说明 fivsevn-spec 中旧文档、历史规范和退役文件的处理方式。

当前目录保留有效规则和仍有用途的源文件。已被替代的规范、一次性导入报告和不再使用的中间文件，在核对引用后删除；旧版本由 Git 历史保留，不另外堆放备份目录。

---

## 1. 基本思路

在结构调整、规范重写、文件合并或拆分时，先区分当前有效内容、仍有独立价值的资料和已被完整替代的副本。

```text
当前有效文档保持清楚；
独立资料按用途保留；
重复规则和无用中间文件核对引用后删除；
历史版本通过 Git 查询和恢复。
```

这样既避免旧文件干扰当前入口，也保留比较和恢复依据。文件年龄、旧名称或一次失败的构建，不单独构成删除理由。

---

## 2. 当前文件与历史版本

### 2.1 当前目录

当前目录保存：

- 正在生效的规则、工具和 schema；
- 仍有独立用途的示例、原始材料与说明；
- 维护和恢复发布所需的状态记录；
- 明确保留的正式内容、草稿和原始素材。

说明文档应描述实际结构和当前操作，不把已经退役的流程继续列为入口。

### 2.2 Git 历史

被新版完整替代的文件和无用中间产物，从当前文件树移除。原文件内容、路径和改动过程仍可通过 Git 历史查看、比较或恢复，不要求长期保留第二份目录副本。

### 2.3 `archive/`

`archive/` 保存历史文件处理规则和归档政策，不存放重复的旧规则本体。需要长期保存且仍有独立用途的资料，应按实际主题归属放置，并说明其身份和用途。

---

## 3. 文件身份与路径

保留内容的稳定 ID、现有公开网址及必要的来源信息。移除过时文件前检查：

- README 和当前文档中的路径；
- 脚本、Actions 与模板中的入口；
- 其他仓库或页面的实际引用；
- 仍需要的唯一示例、字段说明或原始素材。

如果旧文档中存在当前规则尚未覆盖的有效内容，先合并到对应文档，再删除重复版本。纯粹为了保存历史，不另外复制文件或添加退役目录。

---

## 4. 旧文档处理流程

```text
1. 确认替代文档及实际保留范围；
2. 核对文档、脚本和其他消费者的引用；
3. 将仍有效的独有内容合并到当前文档；
4. 删除已被替代的文件及无用中间产物；
5. 同步更新 README、索引与脚本入口；
6. 运行对应校验，保留可追溯的 Git 提交。
```

不确定文件用途时先核实。正式内容、草稿、唯一原图和发布状态不能与无用构建输出一并清空。

---

## 5. 保留内容的归档 frontmatter

有独立价值且明确保留的历史内容，可以使用归档 frontmatter；这不要求把已无用途的临时文件继续留在当前目录。

```yaml
---
module: system
type: note
status: archived
canonical: false
summary: >
  archived
tags: [archive]
visibility: public
source_of_truth: devlog
updated: 2026-03-01
---
```

字段含义：

- `status: archived` 表示文档已归档；
- `canonical: false` 表示它不再是当前规范主版本；
- `summary` 说明保存用途；
- `tags: [archive]` 便于识别归档内容；
- `visibility: public` 表示源文件可公开保留，不强制进入网站目录；
- `updated` 记录实际内容更新日期。

正式文件仍需满足当前[核心字段规范](../content/spec-content-frontmatter-001.md)。

---

## 6. 当前规范入口

当前有效文档应通过以下位置进入：

- 仓库 README；
- 当前主题目录下的正式规范；
- 当前索引或模块映射文件。

README 不应把已退役规则列为正式规范。链接目标删除或移动时，应同步修改引用，不留下已失效的目录说明。

---

## 7. 什么时候可以删除旧文件

旧文件满足以下条件时，可以删除：

- 已经被新版文档完全取代，或没有继续使用的入口；
- README、当前文档、脚本和消费者不再依赖它；
- 有效示例、字段和唯一原始资料已经妥善保留；
- 删除不会影响当前规范的理解、构建或发布；
- 文件及其变更可从 Git 历史追溯。

发布收据、导入游标、去重身份和恢复所需状态具有运行用途，不因文件名像缓存就删除。临时构建结果按各仓库实际生成和清理方式处理。

---

## 8. 最小维护原则

退役规则不继续与新规则平行维护。需要修正当前说明时，直接修改有效版本；需要研究或恢复旧版本时，从 Git 历史定位对应提交。

仍在当前目录保留的历史内容，只在以下情况修改：

- 修正明显错误的链接；
- 明确归档身份和实际用途；
- 修正来源或日期等已有记录中的错误；
- 补充理解该内容所需的上下文。

不为整理旧文件而补造日期、身份、来源或授权。

---

## 9. 推荐提交方式

清理旧文件时，使提交范围和说明能够直接反映实际改动。例如：

```text
chore: Remove superseded commit message guides
chore: Remove unused import reports
refactor: Replace outdated datetime documentation
```

新增有效规则和移除旧规则同时发生时，可按实际需要分开提交，便于检查差异和恢复；不要求为了保存旧文件另建重复目录。
